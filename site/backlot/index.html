    00Overview

    Backlot, a CMS for streaming services

    Rejections that tell the editor exactly what to fix

    Backlot is where streaming services prepare films and series for release, one region at a time. I designed the review loop between editor and publisher, so a rejection is a list of reasons pinned to fields, not a vague note.

    ContextSolo concept. The take-home that got me hired for my last role, rebuilt and extended.

    My roleProduct Designer, end to end

    01The problem

    The work is not hard. The loop is.

    The problem

    The editor needs to know what to fix. The publisher needs to know what changed. Today, neither gets it: the editor guesses, the publisher re-checks everything, and the release slips.

    Every time something comes back, both sides redo work, and the release date does not move.

    02

    North star

    Every round of review should be the last one

    Every decision on this page answers one question: does it remove a round of review? Each feature below shows which part of the loop it cuts.

    The bet

    Rejections repeat because publishers' comments are too vague to act on, not because editors are careless. The biggest gap: I haven't sat with an editor yet. If the bet holds, rejection rounds per episode drop. If they don't, the bet was wrong.

    04

    Two roles

    One episode, two people asking different questions

    EditorAll day

    “What exactly do I fix, and is it ready now?”

    Works region by region, many episodes at once.

    • Which field each reason is on
    • What the region still needs
    • Submit only what changed
    PublisherPer review

    “What changed since I last looked?”

    Decides before a release date, can't re-check everything.

    • Only the fields that came back
    • Who changed what and when
    • Reject with reasons, not a note

    05Features

    Feature 01

    A rejection is a list of reasons

    The publisher approves an item, or sends it back with reasons the editor can act on one by one. Each reason is pinned to its field.

    1. The publisher comments on the metadata row itself. Each comment becomes a reason that carries its field and a category
    2. Flagged rows stay marked on the page, so the editor resolves them in place instead of searching
    3. Reasons resolve one by one. Reject counts them, names who gets the item back, and asks for confirmation first
    4. A flagged field can be unflagged, because publishers are sometimes wrong too
    Cuts the loop at Deliver→Prepare→Review→Release

    Try it

    Flag two fields as the publisher, then fix them as the editor.

    Feature 02

    Region comes first

    Almost every field changes by region: title, synopsis, age rating, release date, rights, audio and subtitles. So the editor picks a region first, and everything under it shows for that region only.

    Cuts the loop at Deliver→Prepare→Review→Release

    Feature 03

    A series is a tree

    A film is one item. A series is a tree: seasons under the series, episodes under each season, files under each episode, and every level has its own metadata and status.

    Feature 04

    The editor never hunts for what is missing

    It sits at the top. Everything the region still needs comes first, above what the upload already filled.

    1. The readiness panel lists what must be complete before the season can be scheduled in this region
    2. Checks show progress, not pass or fail: “4 of 8” tells the editor how much work is left and where to start, “incomplete” only says something is wrong
    3. Every empty field is grouped in “Needs your input”, above what the upload already filled
    4. Values read from the media file, like runtime and codec, can never be edited, because they describe the file itself. Values from the delivery unlock one field at a time, so every change is deliberate
    5. Submit for review hands the episode to the publisher. Save keeps unfinished work without submitting it, so the episode stays under In progress on the dashboard, easy to pick up later
    Cuts the loop at Deliver→Prepare→Review→Release

    The whole page in one pass

    A walkthrough from the season to the episode that blocks it.

    Feature 05

    AI flags, it never fills

    Catch the rejection before the publisher does. A wrong auto-fill is an error nobody sees, so every flag waits for a person.

    1. The AI learns from past rejection reasons. Every reason carries a field and a category, so they can be counted per team and per region
    2. Rules and AI stay apart. A broken rule is a failed check in the Readiness panel, never a guess. The AI only raises judgement calls and says how sure it is
    3. The AI writes nothing on its own. A flag opens its field, or gets dismissed with a reason that stays on record
    Cuts the loop at Deliver→Prepare→Review→Release

    Rules and AI, side by side

    Rule checks pass or fail. AI suggestions name their evidence, and a dismissed flag stays on record.

    Feature 06

    Designed for the delivery that arrives broken

    Automation sits in one step: after upload, the system reads technical metadata and assigns the files it can match. A wrong match is a mistake editors can't see, so the system suggests and the editor confirms.

    1. Processing reads each file’s technical metadata and matches it to its content, so most files are assigned automatically. Only the ones it cannot place wait for the editor
    2. One line reports the result: 24 uploaded, 9 assigned automatically, 15 need the editor
    3. The drop zone stays, so files can be added mid-upload
    4. Files keep their own states (Uploading, Processing, Ready, Needs assignment, Failed), separate from the workflow status of their content
    Cuts the loop at Deliver→Prepare→Review→Release

    The whole upload

    From the drop to the files that need the editor.

    Feature 07

    Every file sits under the content it belongs to

    So a missing one shows as a gap, before a delivery is rejected.

    1. Each film or episode shows how complete its files are (2 of 7), so a gap surfaces before a delivery is rejected
    2. Two views: Content groups files under their film or episode, Files lists them all for bulk work. Language and Type are filters, not groupings
    Cuts the loop at Deliver→Prepare→Review→Release

    Switching views and filters

    Content and Files, then Language and Type as filters.

    Feature 08

    Artwork is chosen by taste, not by country

    Most viewing starts from a recommendation, so the thumbnail does much of the selling. Taste predicts a click better than age or location, so each season carries one thumbnail per taste cluster.

    1. One thumbnail per taste cluster: action, drama, romance and mystery fans each see the scene that speaks to them
    2. Variants are tested against each other in each region, with the time left on the test, so the editor knows when the artwork is final
    3. Each variant shows its click-through rate, and the leader is marked, so the choice is backed by data, not taste
    Cuts the loop at Deliver→Prepare→Review→Release

    Feature 09

    The queue is sorted by what airs first

    Row actions follow the status: Review while content waits, Publish once it is approved. Checks only prove the fields are filled. Judgement on ratings, artwork and sync stays with the publisher.

    Cuts the loop at Deliver→Prepare→Review→Release

    Feature 10

    Once review starts, content is locked

    Changes go through an edit request, not a reopen. It covers new information from outside, like an updated regional age rating, never a mistake in approved work.

    Cuts the loop at Deliver→Prepare→Review→Release
    06

    What I changed

    One label showed me the first version was wrong

    The first version

    The first version allowed one rejection reason per item, and I caught myself labelling rejected items “Multiple Issues”. That label was a symptom, not a reason, so reasons became a list, each pinned to a field and resolvable on its own.

    What I took out

    Most of what I added stayed. Four things didn’t.

    Taken out

    Availability as a ninth status

    On air, Ended and Expired showed up in work queues as if someone had to act on them. They became their own layer, shown only on headers and in the library.

    Cost: two sets of labels to learn.

    Taken out

    An AI score

    “72% likely to be rejected” gave the editor nothing to do. A named reason does.

    Cost: some flags read as less certain.

    Taken out

    Rejections first

    Opening the workspace on Rejections made a bad day the default view. Workflow leads now.

    Cost: rejection cards sit one scroll lower.

    Taken out

    Bulk unlock

    Unlocking every source field at once was fast, but lost which value changed and why. Fields unlock one at a time.

    Cost: multi-field corrections take longer.

    05

    Design system

    Eight states, one icon family.

    Status tells you where the work is. Availability tells you what viewers can see. Two layers, and availability is never a ninth status.

    Workflow status

    To doIn progressPending reviewIn reviewApprovedScheduledPublishedRejected

    Progress

    Not started

    Nothing delivered to this region yet.

    Partial

    Some of the region is ready, not all of it.

    Ready

    Everything for this region is ready.

    Workflow status says where the work is. Progress says how much of a region is ready.

    Availability

    On air

    The series is still releasing episodes in this region.

    Ended

    Every episode is released and still watchable.

    Expired

    The rights window ended in this region. Off the service, all data kept, read-only.

    Not a status. Shown only on series, season and film headers and in the content library, never in a work queue. Neutral outline, no status colour.

    Only the release date earns a spine.

    The release date is the only thing the team cannot move, so it is the only thing that raises urgency.

    Every colour stands for one thing.

    Published has no hue, because most of the library ends up there. Amber and red mean urgency, nothing else.

    Colour by meaning

    08

    What's next

    How I would measure it, and what comes next

    Measure

    Rejection rounds per episode

    The north star. Around it: upload completion time, time to publish and error rate for the editor; thumbnail click-through, its lift over the default, watch start rate and completion rate for the viewer.

    Test

    Test it with editors

    I would test two things first: do the rejection categories cover what publishers actually send back, and do editors trust the split between fields they fill and fields the upload already filled.

    Design

    Design what I scoped out

    Unpublishing, bulk metadata editing and notification routing are each a small product of their own, and each one touches the same loop.

    Later

    Let the system do more of the tagging

    Automatic thumbnail generation and ML-based tagging would feed the taste clusters, with the same rule as the rest of Backlot: it suggests, a person decides.
