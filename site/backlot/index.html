    Backlot, a CMS for streaming services

    Fewer review rounds from
    delivery to release

    Backlot is a concept CMS for streaming teams, taking films and series from delivery to release, region by region. I designed the whole workflow for both sides: publisher and editor.

    ContextThe take-home that got me hired for my last role, rebuilt and extended.
    CategoryB2B SaaS, Streaming CMS
    My roleSolo project: research, flows, UI, prototypes
    Date2026. Take-home: 7 days, extended over 2 weeks
    StatusConcept, Not Shipped
    01The problem

    The work is not hard.The loop is.

    The problem

    For the team: getting one episode ready for one region means uploading its files, filling about forty fields and passing a publisher’s review. Much of it is typing what the file already says, and mistakes only surface at review, where each one costs a round.

    For the service: 86% of streaming operators in a 2026 survey said poor metadata costs them real money, and a wrong value for one region can put a title on air where its rights don’t allow it.

    Finding

    Files arrive broken

    Deliveries come with missing, extra or mislabelled files, and each file has to be assigned to its episode by hand.

    Finding

    Almost every field changes by region

    Title, synopsis, age rating, release date, rights, audio and subtitles each need their own version per region.

    Finding

    Mistakes hide in the structure

    Metadata entered on the wrong level, a season instead of an episode, only shows up at review.

    Finding

    Feedback doesn’t point at a field

    Some tools let a reviewer comment on a field, but a rejection still lands as one status. Nothing groups the reasons, so the editor can’t see at a glance what blocks the release.

    North star

    Release-ready sooner, with less typing

    Every decision on this page aims at the same thing: an episode release-ready sooner, with less typing and fewer review rounds.

    The bet

    Most of the delay is retyping and rework. On an episode page, the editor types 5 of 41 fields; the rest fill in automatically from the file, the delivery and the season. When a rejection also names the field to fix, there is less to redo in the next round. I haven’t tested this with an editor yet.

    Research

    Streaming CMSs are built in-house and rarely shown, so I studied the tools that cover pieces of the workflow: headless CMSs, a video platform, creative review tools, and GitHub’s pull request review, where a reviewer comments on an exact line and the author resolves each comment.

    Role-based dashboards

    Each role starts the day on its own page, with what needs them first.

    1. Editor

      Where I left off, what came back and what blocks release, on one page.
    2. When files from a delivery couldn’t be assigned, a banner opens the page with one button to resolve them.
    3. Missing fields grouped across everything assigned to the editor, so one pass fills the Spanish synopsis for seven items.
    4. A dashboard can’t hold every status, so each role gets the four that matter most to it, in order. The editor’s start with Rejected: the work that came back.

    5. Publisher

      What airs soon, what waits for review, and a banner for the one item that airs within seven days and still needs a decision.
    6. The publisher’s metrics start with Pending review, the queue they have to keep short.
    7. In place of blockers, the publisher sees each region’s deliveries this week and how far along they are.

    Role-based workspaces

    The same menu item has a different name and page for each role: Workspace for the editor, Reviews for the publisher. Each holds only that person’s work, apart from the shared Content library.

    1. Editor

      Everything the editor is working on, in one table sorted by status, because they move many items at once and compare them row by row.
    2. The list runs through all eight statuses, from To do to Published, so nothing the editor touched drops out of view.
    3. Each piece of content sent back shows its reasons on the card, readable before it opens, so a bad review is less to hold in mind.

    4. Publisher

      Only what reaches the publisher. To do and In progress belong to the editor, so the list starts at Pending review. Scheduled stays: the publisher decides what goes live.
    5. The queue is sorted by what airs first and shows how long each item has waited.
    6. Every decision the publisher made: who decided, when, and when it was released. The Content library holds everything; this is only what passed through their hands.
    03Features

    Features

    Eight decisions across the workflow

    1. 01A rejection is a list of reasons
    2. 02AI suggests, the editor accepts
    3. 03The editor only fills what is missing
    4. 04Region is a structural scope, not just a filter
    5. 05The delivery that arrives broken
    6. 06Each row offers only its next step
    7. 07Once review starts, content is locked
    8. 08Thumbnails are chosen by taste, not by country

    Feature 01

    A rejection is a list of reasons

    The publisher approves the content, or sends it back with reasons the editor can act on one by one. Each reason is pinned to its field.

    01

    Comments become reasons

    The publisher comments on the metadata row itself. Each comment becomes a reason with its field and a category.

    02

    Fixed in place

    A flagged row stays marked on the page with the publisher’s note, so the editor fixes it in place.

    03

    Counted before it is sent

    Before anything is sent, Reject shows how many reasons there are and who gets the item back.

    What the publisher sees while reviewing

    When the same reason comes back

    A clear note can still fail. If one reason returns on three episodes of a season, the editor isn’t the problem: the wrong value is coming from upstream. Because every reason carries a field and a category, a repeat can be counted and fixed where it starts: the season, the delivery spec or an automatic check.

    Feature 02

    AI suggests, the editor accepts

    The AI points at likely rejections before the publisher sees them and proposes values like keywords. Nothing is written until the editor accepts. Rule checks pass or fail; AI suggestions name their evidence and how sure they are.

    01

    Built on past rejections

    Suggestions come from past rejection reasons. Each reason carries a field and a category, so they can be counted per team and per region.

    02

    Rules and AI stay apart

    Automatic checks pass or fail by rule. The AI sits apart and only raises judgement calls, saying how sure it is.

    03

    Nothing written on its own

    Accept writes the value, Dismiss asks for a reason. Either way, the decision stays in the activity log.

    The checks panel on the episode page

    Feature 03

    The editor only fills what is missing

    Runtime, codec and audio are read from the file, and the delivery fills most of the rest. What is still missing sits at the top of the page.

    1. Every empty field is grouped in “Needs your input”, above what the upload already filled.
    2. Values from the delivery are locked. Each field unlocks on its own, so every change is deliberate.
    3. Submit hands the episode to the publisher. Save keeps it under In progress, ready to pick up later.
    4. “4 of 8” tells the editor how much is left and where to start. “Incomplete” would only say something is wrong.
    5. Every season and episode page lists what must be complete before it can be scheduled in that region.

    Feature 04

    Region is a structural scope, not just a filter

    Almost all metadata, and the files, rights and dates around it, can differ by region. Content is a tree of series, season, episode and file, each level with its own fields and status, so a season keeps its own metadata apart from its episodes. Age rating rolls up: a season takes the highest rating among its episodes.

    Interactive prototype: Change the region

    Feature 05

    The delivery that arrives broken

    unhappy path

    Deliveries might arrive incomplete or mislabelled. None of it blocks the work: processing places what it can, the upload runs in the background, and every file problem has its own fix.

    1. Processing reads each file’s technical metadata and links it to its episode. Files it can’t place go to Needs assignment.
    2. The upload folds into a panel in the corner, so the editor can open other pages and come back to it.
    3. The drop zone stays open, so files can be added while others are still uploading.
    4. Uploading, Processing, Ready, Needs assignment and Failed belong to the file, apart from the episode’s workflow status.

    Resolving the files processing couldn’t place

    Each problem gets its own fix: assign files in bulk, keep or replace a duplicate master, or create the episode a file points to.

    Feature 06

    Each row offers only its next step

    Review while an episode waits, Publish once it’s approved: each row shows only the action its status allows.

    Feature 07

    Once review starts, content is locked

    While the publisher reviews, every field is read-only. After approval, a change needs an edit request: a region may ask for a change, or the publisher may have approved a mistake. Each request reopens one section at a time.

    Feature 08

    Thumbnails are chosen by taste, not by country

    Most viewing starts from a recommendation, so the thumbnail does much of the selling. Each season carries one thumbnail per taste cluster, and each variant is tested per region.

    01

    One thumbnail per taste

    Action, drama, romance and mystery fans each see the scene most likely to make them click.

    02

    A/B tested per region

    Variants are tested against each other in each region, with the time left on the test, so the editor knows when the artwork is final.

    03

    Backed by click-through

    Each variant shows its click-through rate, and the leader is marked.

    04

    What I changed

    Why I moved from a single rejection modal to field-pinned reasons

    The first version

    The first version allowed one rejection reason per item, and I caught myself labelling rejected items “Multiple Issues”. That label said something was wrong without saying what, so reasons became a list, each pinned to a field and resolvable on its own.

    What I took out

    Most of what I added stayed. Four things didn’t.

    Taken out

    Availability as a ninth status

    On air, Ended and Expired showed up in work queues as if someone had to act on them. They became their own layer, shown only on headers and in the library.

    Cost: two sets of labels to learn.

    Taken out

    An AI score

    “72% likely to be rejected” gave the editor nothing to do. A named reason does.

    Cost: some flags read as less certain.

    Taken out

    Rejections first

    I didn’t want an editor’s day to start with what went wrong, so the workspace opens on their work and rejections sit below it.

    Cost: rejection cards sit one scroll lower.

    Taken out

    Bulk unlock

    Unlocking every source field at once was fast, but lost which value changed and why. Fields unlock one at a time.

    Cost: multi-field corrections take longer.

    Design system

    Eight states, one icon family

    Status tells you where the work is. Availability tells you what viewers can see.

    Workflow status

    To doIn progressPending reviewIn reviewApprovedScheduledPublishedRejected

    Progress

    Not started

    Nothing delivered to this region yet.

    Partial

    Some of the region is ready, not all of it.

    Ready

    Everything for this region is ready.

    Progress says how much of a region is ready, apart from its status.

    Availability

    On air

    The series is still releasing episodes in this region.

    Ended

    Every episode is released and still watchable.

    Expired

    The rights window ended in this region. Off the service, all data kept, read-only.

    Not a status. Shown only on series, season and film headers and in the content library, never in a work queue. Neutral outline, no status colour.

    Every colour stands for one thing

    Published has no hue, because most of the library ends up there. Amber and red mean urgency, nothing else.

    Colour by meaning
    Status
    One hue per status, except Published, which stays neutral. Never accent, never amber.
    Provenance
    Measured and asserted share a quiet edge. Suggested gets an accent edge and a sparkle. Manual lifts one step.
    AI
    Accent 300 ink and the 12% tint, used only for proposals.
    Urgency
    Amber inside 7 days of release. Red once release has passed.

    Only the release date can make a row urgent

    The release date is the only thing the team cannot move, so it is the only thing that raises urgency.

    What's next

    How I would measure it, and what comes next

    Time from delivery to release-ready

    Per region, with the review rounds it took, the fields the editor still typed and the thumbnail clicks. One warning sign: the same rejection reason back on three episodes of a season.

    01Measure

    Test it with editors

    I would test two things first: do the rejection categories cover what publishers actually send back, and do editors trust the split between fields they fill and fields the upload already filled.

    02Test

    Design what I scoped out

    Unpublishing, bulk metadata editing and notification routing are each a small product of their own, and each one touches the same loop.

    03Design

    Let the system do more of the tagging

    Automatic thumbnail generation and ML-based tagging would feed the taste clusters, and a person would still confirm each one.
